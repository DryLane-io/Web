Facts

A time-series store that lives inside your process and answers in microseconds.

8.7× DuckDB's ingest rate. Facts on 1 core, DuckDB on 32. 0.2 µs for the latest value, in-process. DuckDB takes 4.3 ms. 15× QuestDB's ingest over the wire, on one connection against eight. 39 µs for the latest value over the network. InfluxDB takes 56 ms.

The honest loss: Facts stores about 96 bytes per point, while DuckDB and QuestDB compress to about 25. That's the price of keeping columns raw for SIMD scans.

What it is
An embedded time-series engine. No server to deploy and no network hop to query. It holds billions of timestamped facts and answers range, tag, scan and aggregate queries with SIMD.
The problem
Lots of time-series data, queried fast, usually means a cluster of database nodes to run, tune and pay for. Facts does it on one box.
For example
Store every tick from thousands of sensors, then ask what device 4200 did between 09:00 and 09:05. The answer arrives before a network round-trip would have finished.
The data model

A fact is a timestamp and a tag. Attach typed columns for fixed-size fields and a blob for everything else. Simple records are why it's fast.

the core

Timestamp + tag

The timestamp orders the fact. The tag names its series: a device, a symbol, a driver, a log source.

Everything is indexed on that pair, so "this tag, this window" works with nothing else declared.

fixed size

Columns

Typed columns for a price, a temperature, an RPM. They're stored columnar, so a SIMD kernel streams one column at full memory bandwidth.

A query reads only the column it asks for, never the rest of the row.

variable size

Blob

Log lines, JSON, packets, Dry.Wire records. Stored opaque, with an optional plug-in codec such as LZ4 that decompresses transparently on read.

Good for logs and journals. See the Log Viewer.

Built to stay up
capacity

Limits

Billions of records per box. The ceiling is your disk, with optional retention that evicts the oldest data.

Up to about 16 million series per shard and 256 MiB per blob.

scale out

Shards

Independent shards for parallel ingest and query. Throughput scales with cores, with no cross-shard coordination on the hot path.

on disk

Segments

Immutable, self-describing segments, each checksummed and recoverable on its own. One bad block never takes the dataset down.

stays up

Failover

Replication with veto-based failover. A stale replica can't win an election, so there's never a split-brain and the loss window is bounded. Break it yourself.

crash-safe

Durability

A periodic checkpoint sets the maximum loss window, and every segment verifies itself on open. Power loss doesn't corrupt the store.

runs anywhere

Reach

SIMD-tuned for Intel, AMD and ARM, on Windows and Linux. The same engine on a server rack or a $35 board.

Ingest runs about an order of magnitude ahead of QuestDB and two ahead of InfluxDB. The most common dashboard query, the latest reading for each sensor, comes back in tens of microseconds.

Medians and p99 from our open harness (Facts.Benchmarks, --tier b) on real TSBS cpu-only data, each engine at its best configuration. Why the gap: Facts speaks a compact binary wire format, while QuestDB and InfluxDB use text line protocols where every number is spelled out in ASCII and parsed again. Durable, too: re-run with every engine writing to NVMe instead of RAM, Facts held 25 M rows/s. Where the rivals win: they compress columns at rest, and both are full query languages (SQL and Flux, joins, ad-hoc queries) with far bigger ecosystems. InfluxDB's v2/Flux engine is also known to be slow on these access patterns; v3 would narrow the query gap.

Crash-tested on Linux and Windows

The harness kills the process mid-write, tears chunks on disk and corrupts the index, then checks what survives. Every test passes on both platforms.

  • Killed mid-write. Every flushed record survives; only the unflushed tail is lost, as designed.50 of 50 flushed records recovered, 0 failures
  • Torn chunk on disk. Verify-on-open cuts at the damage and keeps everything before it.656 records kept before the torn chunk, 0 failures
  • Torn index, with and without blobs. The index is rebuilt from the columns and checked.1,311 survivors verified, sealed blobs intact, 0 failures
  • Index rebuilt from scratch. Compared record by record against the column data.42,599 records verified, 0 failures
  • Correctness. Typed columns, SIMD scan, range predicates, info getters, live scan, and blob reads across sealed and active segments.6 of 6 micro-tests pass, blob read check passes
